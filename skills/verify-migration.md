# /verify-migration

Verify a migrated Power Code app behaves as expected, scoped to a specific `vibe-history.json` version. Generate Playwright tests from the source, run them against the **deployed** Power Apps player, and auto-raise GitHub issues on failure.

**Use when** the user wants to:
- Confirm a fresh `/migrate` Mode A produced a working app
- Confirm a `/migrate` Mode B (incremental re-extraction) didn't break anything
- Re-run an earlier version's tests to check for regressions
- Generate test scaffolds for new features added in a recent update

Pairs tightly with [version-control.md](version-control.md) — every test belongs to a version in `vibe-history.json`.

---

## Three modes

### 1. Generate

Scan the Power Code project (or the `vibe-pending-update.json` for an incremental run) and write `.spec.ts` files into `./tests/specs/v{version}/`.

**Always ask the developer first** which depth they want:

> Which generation depth?
>   1. Smoke tests only — one test per page, "loads without errors and renders main heading". Fast, catches the big regressions.
>   2. Smoke + happy-path per feature — adds one happy-path test per detected user action (form submit, button click that mutates state).
>   3. Full coverage attempt — happy-path + error states + edge cases. Slow generation, lots of human review.

Generate accordingly. Keep test names human-readable — they double as the test plan.

**Test file template:**
```typescript
// Auto-generated by /verify-migration
// Reviewed:  not yet                 ← developer flips to "yes" after manual review
//
// @addedIn   v1.0.0
// @feature   <name>
// @critical  yes|no
//
// Edit freely. Re-generate only with --regenerate.

import { test, expect } from '@playwright/test';

test.describe('<Feature> — v1.0.0', () => {
  test('<readable scenario>', async ({ page }) => {
    await page.goto('/');
    // ...
  });
});
```

**For incremental runs after `/migrate` Mode B:** read `vibe-pending-update.json`, generate tests only for files in `changedFiles.added` and `changedFiles.modified`. Place them in `tests/specs/v{toVersion}/`.

### 2. Run

Invoke the Node CLI. It pops a headed Chromium window so the developer can watch tests execute.

```powershell
# First time only — sign in to Microsoft account, saves auth state
node vibe-verifier/index.js --setup-auth

# Run all version specs
node vibe-verifier/index.js

# Run only the latest version
node vibe-verifier/index.js --latest

# Run v1.0.0 → latest
node vibe-verifier/index.js --since v1.0.0

# CI mode — no window, no GitHub issues
node vibe-verifier/index.js --headless --no-report
```

The runner constructs the deployed URL from `power.config.json` (`environmentId` + `appId`). Override with `--app-url <URL>` if needed.

### 3. Diagnose

When a test fails, read the captured artifacts:
- `tests/results/v{version}/{date}/report.json` — full Playwright report
- `tests/results/v{version}/{date}/trace-N.zip` — open with `npx playwright show-trace <path>`
- `tests/results/v{version}/{date}/failure-N.png` — screenshot at moment of failure

Apply the [diagnose](diagnose.md) skill to the failure. State a hypothesis based on the error, the screenshot, and a quick read of the failing test's `.spec.ts`. Draft a one-paragraph explanation suitable for the GitHub issue body.

The CLI auto-posts to GitHub by default (`gh issue create` or comments on an existing open issue with the same test name + version). Use `--no-report` to suppress.

## Files owned by /verify-migration (at project root)

| Path | Owner | Purpose |
|---|---|---|
| `tests/specs/v{version}/` | `/verify-migration` (generate) | One folder per migration version. Tests stay there forever — even after the version is no longer "latest". |
| `tests/results/v{version}/{date}/` | `vibe-verifier/lib/runner.js` | Per-run artifacts: report.json, traces, screenshots. Safe to delete old ones. |
| `vibe-verifier/.auth/state.json` | `--setup-auth` | Saved Microsoft account session. **Gitignored** — contains tokens. |
| `vibe-history.json` `testResults` | `vibe-verifier/lib/runner.js` | Appended per-version after each run: `{ passed, failed, skipped, runAt, durationMs }`. |

---

## Prerequisites

Before the first run:
- `npm install` inside `vibe-verifier/` and `npx playwright install chromium`
- `gh` CLI installed and authenticated (`gh auth login`) — only needed if reporting is on
- `power.config.json` populated with `environmentId` and `appId` (the migration step does this)
- The app has been pushed at least once (`npx power-apps push`)
- `--setup-auth` has been run once and the saved state hasn't expired (~2 weeks)

## Workflow integration

| Trigger | Behaviour |
|---|---|
| End of `/migrate` Mode A (v1.0.0 created) | Ask the developer: *"Generate baseline verification tests for v1.0.0 now? (Recommended)"* — if yes, invoke generate mode at smoke depth (ask if they want deeper). If no, just print the command they'd run later: `node vibe-verifier/index.js --setup-auth && /verify-migration` |
| End of `/migrate` Mode B (v1.X.0 applied) | Ask: *"Generate verification tests for the {N} changed features in v1.X.0?"* — incremental generate, only the files in `vibe-pending-update.json`. |
| Developer types `/verify-migration` | Run the full skill: ask depth → generate (or skip if specs exist) → ask to run → if run, invoke CLI → diagnose any failures. |

## Rules

1. **Generated tests must be reviewed before being trusted.** Mark `// Reviewed: not yet` at the top; the developer flips it to `// Reviewed: yes`. AI-generated assertions can be wrong about what's "expected".
2. **Tests live in their version folder forever.** When a feature is modified in a later version, update the existing test in place and bump the `@lastUpdated` comment — don't duplicate it in the new folder. The exception: a brand-new feature added in v1.X.0 lives in `tests/specs/v1.X.0/` from inception.
3. **Never commit `vibe-verifier/.auth/`** — it contains authentication tokens. The `.gitignore` is in place; double-check.
4. **Tests run against the deployed app, not local dev.** This is intentional (catches CSP, real connector errors). It also means tests pollute real Dataverse — prefer test data with a `[TEST]` prefix and clean up in `test.afterEach`.
5. **GitHub issue dedupe is by `<testName> @ v<version>` in the title.** If the same test fails again, a comment is added rather than a new issue created — don't manually close-and-reopen unless you've confirmed the test was fixed.
6. **Auth tokens expire.** If the runner hits a login redirect, re-run `--setup-auth`. The CLI warns when the saved state is over 14 days old.
